# New production-log performance rescan — 16 November 2026

Analyzed all 338 lines and all 65 completed requests in the supplied November 13 journal. Requests are joined by request UUID, not adjacent log lines. Interleaving had assigned some slow durations to the wrong pages in the supplied summary.

## Findings and changes

- `/target_mappings` really took 12,580 ms. The default ICS form no longer eagerly loads every unused office/FCO/block catalogue. Its existing mode-change JSON request still supplies authoritative office/block values.
- `/vrps/new` spent 7,192 ms preparing the location browser attribute; `/users/new` spent 7,618 ms preparing form options. Versioned shared file caches now let Puma workers reuse prepared/escaped payloads. LG directory rows, sorted master attributes and module location attributes also reuse these caches.
- Dropdown revision probes now cover the actual source module instead of scanning every unrelated module on each field; a controller reuses the source revision across fields. Source status changes, edits, inserts and deletes still invalidate the payload; negative/global scopes retain global invalidation. Payload filters, values, JSON types and ordering are unchanged.
- Master sorting reuses the field's normalized key instead of transliterating it for every row. The existing Ruby sort and tie ordering remain.
- `/jj-mapped-farmers` was the request with an 8,199 ms external JJ catalogue stage (not `/vrp-agreements`). A blank admin report now opens first and loads its required JJ picker in a separate authorized Turbo frame. Selected-mobile reports, other roles and exports retain the synchronous path. No-JavaScript fallback remains.
- `/modules/office-list` similarly opens its header first and fetches its existing fresh table in a separate frame. Search, pagination and export are initialized for that frame; no additional office-data TTL was introduced. No-JavaScript fallback remains.
- The analysis script's syntax error was fixed, with a regression test for interleaved logs.

Bill List and payment/training/target pages were included in render and role checks. Earlier committed bill/list optimizations remain in place; this patch also reduces shared catalogue, dropdown and GC work affecting those pages. This is not a claim that every remaining production bottleneck has been eliminated.

Corrected attribution: 8,267 ms belongs to `/modules/other-target`; 8,044 ms belongs to `/modules/other-target-with-farmer`; 2,187 ms belongs to `/modules/training-form-list`. `/target_mappings/list` is 1,933 ms, `/vrp-agreements` 639 ms, and `/modules/user-hierarchy-mapping` 125 ms.

## Blue progress bar and timing limits

Turbo's installed default progress delay is 500 ms. Slow backend navigation makes that bar appear. The progress indicator was not hidden. The journal's Farmer 360 pages themselves took 16, 70, 112 and 149 ms, so they do not establish a universal 15 ms target.

External work moved to a frame still takes upstream response time. It is now independent of initial navigation; users must wait for remote rows/options before using them. Large payload transfer, browser rendering, network latency and concurrent production load remain unmeasured locally. A maximum 15 ms for all complete pages cannot be guaranteed from these checks.

## Cache correctness and operations

Shared caching is enabled in production only, under `tmp/cache/shared-form-catalogues`. Each catalogue has one file slot (plus its lock), keyed by environment, database identity, source and live revision. Code fingerprints reject payloads generated by another application version. Fresh uncached revision checks guard cold writes against concurrent edits. RAM retention is one hour and shared retention one week; live source revision and code identity control freshness, rather than waiting for TTL expiry. File/lock failures fall back to building normally. File locks coalesce fills across workers on the same host. Multiple hosts need separate prewarming; this is not a distributed cache service.

No business records, database schema, billing formulas or authorization predicates were intentionally changed. Async delivery for the two external catalogues is the deliberate visible behavior change. Tests compare loaded options/table data, selected-mobile behavior, access denial, escaping, cache invalidation and exports; they do not prove every possible production workflow.

After deployment/restart, prewarm on each application host using the same release, OS user and cache directory as Puma:

```sh
RAILS_ENV=production bundle exec rails runner script/warm_form_catalogues.rb
```

This reads master data and writes caches only, without external HTTP or business-data writes. It also warms all five location master sorts and LG directory rows. Running it after large imports avoids the first visitor doing those fills. Deployments with a non-shared release `tmp` directory must warm the active release. No deployment or production warmup was performed here.

For actual worker/DB pressure after rollout, the existing read-only diagnostic is available:

```sh
bash script/performance_runtime_snapshot.sh javika_production 6
```
